📖 Overview

What is Ethio Telecom RMS?

A backend REST API for managing customer support tickets, technician assignments, and appointment scheduling with real-time queue tracking and priority-based ordering.

Core Features

🎫 Ticket Management

Customers report issues, get assigned technicians, track progress, and leave reviews. Support for priority-based queue ordering (URGENT, HIGH, MEDIUM, LOW).

📊 Real-Time Queue

Live queue position calculation with ETA. Position = ahead × 45 minutes (configurable). FIFO ordering within priority levels.

👥 Role-Based Access

Three roles: CUSTOMER (create tickets, view own), TECHNICIAN (resolve assigned), ADMIN (manage all, invite staff, audit).

🔐 JWT Security

Short-lived access tokens (15 min). Long-lived rotating refresh tokens (30 days, single-use). Automatic revocation on logout.

📅 Appointments

Customers reserve branch visits. Prevents double-booking. Staff can mark completed. Time-slot validation.

📋 Admin Control

Invite technicians/admins. Ban/unban users. Force password reset. View full audit trail. List technician workload.

Tech Stack

  • Framework: Next.js 15 (App Router)
  • Database: Neon Postgres (production) / SQLite (development)
  • ORM: Prisma
  • Auth: JWT (Jose), Bcrypt password hashing
  • Email: Resend API
  • Validation: Zod schemas
  • Testing: Playwright
  • Deployment: Vercel
Base URLs:

🔐 Authentication & Authorization

JWT Flow

  1. Register/Login: POST /api/auth/register or /api/auth/login → receive accessToken + refreshToken
  2. Use Access Token: Add header Authorization: Bearer {accessToken} to all requests
  3. Token Expiry: Access token expires in 15 minutes. Refresh to get new pair.
  4. Refresh Token: POST /api/auth/refresh {refreshToken} → new accessToken + new refreshToken (old is revoked)
  5. Logout: POST /api/auth/logout {refreshToken} to revoke one token or {allDevices: true} to revoke all

Tokens Never Expire in DB

Refresh tokens are stored hashed in the database. They are valid until explicitly revoked (via refresh, logout, or password change). This allows persistent login across device restarts.

Password Reset

  • Forgot Password: POST /api/auth/forgot-password {email} → email with reset token (dev mode also returns token)
  • Reset: POST /api/auth/reset-password {token, newPassword} → revokes all existing sessions
  • Change Password: POST /api/auth/change-password {currentPassword, newPassword} (requires Bearer token)

Security Features

  • Bcrypt Hashing: Passwords hashed with 10 rounds, constant-time comparison
  • Refresh Token Rotation: Each refresh invalidates the previous token
  • Single-Use Reset Tokens: 60-minute TTL, marked used after redemption
  • Banned Account Check: Banned users cannot login (403 "Account has been banned")
  • Ownership Verification: Customers only see own resources, techs only see assigned tickets
  • Session Revocation: Password change revokes all other sessions

🔄 Common Workflows

Customer Reporting Issue

  1. POST /api/auth/register → get accessToken
  2. POST /api/tickets {subject, category, description} → get ticketNumber
  3. GET /api/tickets/{id}/queue → check queue position, ETA
  4. Receive notification when technician assigned
  5. POST /api/tickets/{id}/review {rating, comment} → review after fix

Technician Fixing Ticket

  1. POST /api/auth/login → get accessToken
  2. GET /api/tickets → view assigned tickets
  3. PATCH /api/tickets/{id} {status: "IN_PROGRESS"}
  4. POST /api/tickets/{id}/resolve → mark fixed
  5. Customer gets notification to review
  6. If issue persists: POST /api/tickets/{id}/reopen

Admin Managing Staff

  1. POST /api/auth/login (admin account)
  2. POST /api/admin/users {email, name, role: "TECHNICIAN"} → invites staff
  3. GET /api/technicians → view workload
  4. POST /api/tickets/{id}/assign {technicianId} → assign ticket
  5. GET /api/admin/audit → view all actions
  6. POST /api/admin/users/{id}/ban → ban problematic user

Booking Appointment

  1. POST /api/auth/register or login
  2. POST /api/appointments {branch, slotTime, notes} → reserve slot
  3. PATCH /api/appointments/{id} {status: "COMPLETED"} → staff marks done

❌ Error Responses

Standard Error Format

{
  "error": "Error message",
  "details": {...}  // optional
}

HTTP Status Codes

Code Meaning Examples
200 Success (GET, PATCH) Fetched resource, updated successfully
201 Created POST /api/tickets, POST /api/appointments
400 Bad Request Invalid input (missing required field, invalid email format)
401 Unauthorized Missing/invalid/expired token, banned account
403 Forbidden Insufficient permissions (customer trying to access admin endpoint)
404 Not Found Resource doesn't exist (ticket ID, user ID)
409 Conflict Email already in use, double-booked appointment slot, already banned
500 Server Error Database error, uncaught exception

Common Errors

  • "Invalid email or password" → 401. Check credentials or account banned.
  • "Email already in use" → 409. Try different email or password reset.
  • "This ticket is not assigned to you" → 403. Tech can only resolve own tickets.
  • "Cannot ban yourself" → 400. Admin cannot ban their own account.
  • "Validation failed" → 422 (+ details). Check field types, required fields.

📊 Queue System

Queue Ordering Algorithm

  1. Sort by Priority: URGENT → HIGH → MEDIUM → LOW
  2. FIFO within Priority: Older tickets first
  3. Calculate Position: Count tickets ahead with same/higher priority
  4. Estimate ETA: position = ahead × 45 minutes (configurable via AVG_HANDLE_MINUTES env var)

Example Queue

Queue (5 total tickets):
  Pos 1: Ticket#1 URGENT  (0 ahead, ETA: 0 min) ← currently handled
  Pos 2: Ticket#2 URGENT  (1 ahead, ETA: 45 min)
  Pos 3: Ticket#3 HIGH    (2 ahead, ETA: 90 min)
  Pos 4: Ticket#4 HIGH    (3 ahead, ETA: 135 min)
  Pos 5: Ticket#5 MEDIUM  (4 ahead, ETA: 180 min)

Your ticket (ID: xyz) is at position 3 with 2 tickets ahead. ETA: 90 minutes.

Real-Time Updates

Queue position updates as tickets are resolved. GET /api/tickets/{id}/queue returns live data (position, ahead, estimatedWaitMinutes).

Configuration

  • AVG_HANDLE_MINUTES: Environment variable (default: 45). Minutes per ticket. ETA = ahead × AVG_HANDLE_MINUTES.
  • REFRESH_TTL_DAYS: Refresh token lifetime (default: 30 days).
  • Access Token TTL: Fixed at 15 minutes (hardcoded).

Register & Get Tokens

  -H "Content-Type: application/json" \
  -d '{
    "name": "Abebe Kebede",
    "email": "abebe@example.com",
    "password": "SecurePass123",
    "phone": "+251911111111"
  }'

Response:
{
  "data": {
    "accessToken": "eyJhbGc...",
    "refreshToken": "base64encodedtoken...",
    "user": {
      "id": "cms5...",
      "name": "Abebe Kebede",
      "email": "abebe@example.com",

curl -X POST https://ethio-telecom-rms.vercel.app/api/tickets \

  -H "Content-Type: application/json" \

    "priority": "HIGH"

{
  "data": {

    "status": "OPEN",
    "priority": "HIGH",
    "createdAt": "2026-07-29T...",
    ...
  }
}

Check Queue Position

curl -X GET "https://ethio-telecom-rms.vercel.app/api/tickets/{ticketId}/queue" \
  -H "Authorization: Bearer {accessToken}"

🚀 Setup & Deployment

Local Development

# Clone & install
git clone https://github.com/theodore-digicom/ethio-telecom-rms.git
cd ethio-telecom-rms
npm install

# Setup database (SQLite)
npx prisma db push
npm run db:seed

# Start dev server
npm run dev
# API at http://localhost:3000
# Docs at http://localhost:3000/
# OpenAPI Spec at http://localhost:3000/api/swagger.json

# Run tests
npx playwright test

Environment Variables

DATABASE_URL=file:./test.db              # SQLite local, or Postgres in prod
JWT_SECRET=<64-char-random-key>         # Sign JWTs
REFRESH_TTL_DAYS=30                     # Refresh token lifetime
AVG_HANDLE_MINUTES=45                   # ETA calculation
EMAIL_FROM=noreply@theo.et              # Verified Resend domain
APP_URL=http://localhost:3000           # For reset links (update to prod domain)
RESEND_API_KEY=re_xxxx                  # Resend API key

Production (Vercel)

# Push to GitHub
git push origin main

# Vercel auto-deploys on push to main
